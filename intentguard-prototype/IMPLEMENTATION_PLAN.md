### ⚠️ 이 환경의 결정적 제약 (실험 설계에 직접 영향)

이 세션은 **원격 클라우드 컨테이너**에서 실행 중이며, 컨테이너는 세션 시작 시
새로 생성되었다. 따라서 `~/.claude/projects/` 에는 **이번 세션의 transcript 1개**
밖에 없다.

```
~/.claude/projects/-home-user-threadshot/
  85bd9da2-....jsonl        ← 이번 세션. 42 lines. 인간 메시지 1개.
```

명세 §2 가 요구하는 조건 —
여러 세션 / 요구사항 추가·변경·취소·임시변경·재활성화가 존재하는 장기 프로젝트 —
는 **이 컨테이너 안에 존재하지 않는다.**

따라서:

- STEP 1~3 (parser / filter / 샘플 생성)은 여기서 완료한다.
- **STEP 4 이후의 실제 벤치마크는 사용자의 로컬 머신**
  (진짜 `~/.claude/projects/` 이력이 쌓인 곳)에서 실행해야 한다.
- 이 프로토타입 CLI는 **경로만 바꾸면 로컬에서 그대로 동작**하도록 만든다.
  (`--claude-home`, `--project` 옵션)

이것은 실패가 아니라 STEP 1 의 산출물이다. 명세 §31 이 말한
"외부 제품이 통제하는 저장소 구조에 의존하는 비용"의 첫 번째 실측 데이터다.

### 발견한 실제 JSONL 스키마 (v2.1.263)

한 줄 = 한 JSON 객체. `type` 필드로 구분되며 **메시지가 아닌 레코드가 다수 섞여 있다.**

관측된 `type` 값:

| type | 개수(이 세션) | 의미 |
|---|---|---|
| `attachment` | 15 | 자동 주입 context (environment, model, skills, date, prompt_snapshot …) |
| `assistant` | 9 | 모델 출력 (text / thinking / tool_use) |
| `user` | 5+ | **인간 메시지와 tool_result 가 같은 type 을 공유** |
| `atis-latch` | 3 | 내부 상태 레코드 |
| `queue-operation` | 2 | 내부 큐 레코드 |
| `last-prompt` | 2 | 내부 캐시 레코드 |

문서화되지 않은 다른 값(`summary`, `file-history-snapshot`, `system`, `x-*`)도
버전에 따라 등장하므로 parser 는 **allowlist 가 아니라 명시적 라우팅 + 미지 타입 카운트**로 처리한다.

### `type: "user"` 안에서 인간과 비인간을 가르는 실제 필드

**핵심 발견: `role === "user"` 는 인간 메시지의 근거가 전혀 되지 못한다.**

진짜 인간 프롬프트:
```json
{
  "type": "user",
  "message": { "role": "user", "content": "<string>" },
  "origin": { "kind": "human" },      // ← 가장 강한 신호 (신버전에만 존재)
  "promptSource": "sdk",              // 로컬 CLI 는 "cli"/"user"
  "promptId": "f5ad9106-…",
  "permissionMode": "auto",
  "isSidechain": false
}
```

tool 실행 결과 (같은 `type: "user"`):
```json
{
  "type": "user",
  "message": { "role": "user", "content": [ { "type": "tool_result", … } ] },
  "toolUseResult": { … },
  "sourceToolAssistantUUID": "133b72ec-…",   // ← 결정적 신호
  "promptId": "f5ad9106-…"                   // ← promptId 는 tool_result 에도 있다
}
```

즉 **`promptId` 존재 여부로 인간 메시지를 판별하면 100% 오분류**한다.
이 세션에서 tool_result 7개가 전부 같은 `promptId` 를 물려받았다.

판별에 실제로 쓸 수 있는 신호 (우선순위 순):

1. `toolUseResult` 또는 `sourceToolAssistantUUID` 존재 → tool 결과
2. `content` 배열에 `tool_result` 블록 존재 → tool 결과
3. `isSidechain === true` → sub-agent 내부 대화
4. `origin.kind === "human"` → 인간 (신버전 한정, 구버전엔 없음 → 부재를 근거로 배제 금지)
5. 위를 통과한 뒤 **텍스트 레벨 정제** 필요

### 텍스트 레벨 오염 (인간 메시지 안에 섞여 들어오는 것)

인간 프롬프트로 분류된 뒤에도 본문에 다음이 주입된다:

- `<system-reminder>…</system-reminder>` — 이번 세션 첫 메시지에도 2개 존재
- `<command-name>/foo</command-name>`, `<command-message>`, `<command-args>` — slash 확장
- `<local-command-stdout>` — 로컬 명령 출력
- `Caveat: The messages below were generated by the user while running …`
- `<wake reason="…">`, `<event source="github" …>`, `<untrusted_external_data>`
- `[Image #1]`, `[Request interrupted by user]`
- IDE 선택 영역 / 붙여넣은 스택트레이스 / 긴 코드

→ 정제 후 남는 것이 **실제 인간이 타이핑한 텍스트**다.

## STEP 2 — Parser + Raw Message Filtering (완료)

`src/parse.js` + `src/filter.js`.
LLM 호출 **0회** (비용 $0). Stage 1 은 결정론적 규칙으로 처리한다.
LLM 은 Stage 2(분류) 이후에만 투입한다 — 쓰레기 입력 위에 돈을 쓰지 않기 위함.

분류 버킷 (명세 §6):
`HUMAN_INTENT` / `HUMAN_CONTEXT` / `HUMAN_CONFIRMATION` / `HUMAN_CORRECTION` /
`PASTED_CONTENT` / `ERROR_LOG` / `TOOL_OR_SYSTEM_CONTENT` / `LOW_INFORMATION` / `UNKNOWN`

`HUMAN_CONFIRMATION` · `LOW_INFORMATION` 은 독립 Requirement 로 만들지 않고
직전 human 메시지들을 `context_message_ids` 로 연결한다 (명세 §6).
